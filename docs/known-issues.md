## 未解決

### 読みやすさ・構成（駅ページ、スマホ幅で確認）
- **最初の画面に事実がない**：路線のラベル、大きな見出し、説明文、ボタンだけで1画面が終わる。1K参考家賃は写真の下（約1.4画面目）で初めて出る。各条件の根拠は7画面近く下にある。
- **「駅＋テーマ」で来た人が答えを見つけにくい**：目的のテーマ（例：飲み歩き）は条件一覧の下の方にあり、ページ上部やテーマページから該当箇所へ飛べない。
- **「暮らしのポイント」本文の羅列**：「A／B／C」「A・B・C」が文章のように並ぶ。根拠欄と同様に、項目ごとの表示にしたい。
- **出典名・更新日が本文に混ざる**：「GO TOKYO（2025-12-19更新）：…」のような、出典の原文がそのまま文の途中に入る。
- **文字サイズ・色の種類が多い**：9pxから48pxまで十数種類。本文は15px・細め・グレーで、見出しとの差が分かりにくい。
- **ページが長い**：スマホ幅で約8.7画面分。写真が暮らしの情報より先に長く続く。

### 検索（SEO）
- **「駅名＋治安」で検索されているが、ページに記載がほとんどない**（現状は池袋のみ）。書く場合は、犯罪統計などの出典つきの事実だけにする。
- **「路線図」「構内図」系の検索が上位なのにクリックされない**：どのページが当たっているか、今の集計では分からない。
- **READMEの公開URLの記載が古い**：本番の正本は `machierabi.3f7735.org`（`worker/domain-redirect.mjs` が `machierabi-annai.kake-web.workers.dev` から301転送）。READMEは workers.dev を前提に書かれたまま。

### 計測（Search Consoleの書き出し）
- クエリとページを別々の表で取っているため、「どのクエリがどのページに当たったか」が分からない。
- デバイス（スマホ／パソコン）の軸がない。スマホ中心かどうかを数字で確認できない。
- クエリ表が、スプレッドシートの1000行の上限に近づく可能性がある。
- 同じ期間の書き出しが、同じ日に複数回実行されている記録がある。

### 検証環境
- **リポジトリ内の公開用HTML（`public/` 配下）が本番より古いことがある**：本番はデプロイ時にビルドされるため、`main` にコミットされたHTMLは古いまま残る場合がある（2026-11-27時点で、駅ページのタイトル・説明文・見出しが本番と異なっていた）。
- 実機のスマホでの見え方は未確認（ヘッドレスのChromeを390px幅にして確認している）。
- 検証環境では地図タイルが読み込まれず、地図まわりの見え方は確認できていない。

## 解決済み

### 2026-11-27（PR #5 追加分）
- **冒頭の4ブロックが左端に真っ平に揃い、目が滑る**
  - 原因：見出し・読み・一言の特徴・紹介文が、同じ左端・似た余白で縦に並んでいた。見出しが48pxと大きく、それ以外との差が大きさしかなかった。
  - 対応：一言の特徴に左の太線、紹介文に字下げ。見出しは小さく太くした。
- **見出しと本文の区別がつきにくい（要点・暮らしのポイント）**
  - 原因：見出しと本文が同じ左端で、違いが文字の色と太さだけだった。
  - 対応：本文に左の細線と字下げ。根拠欄と同じ見せ方に統一。
- **見出し・キャプション・要約の文末に「。」が付いている**
  - 原因：見出しを文として書いていた。写真キャプションは元データの文末の「。」をそのまま表示していた。
  - 対応：見出しから「。」を削除。キャプションと根拠欄の要約は、表示時に文末の「。」を外す。
- **根拠欄の開閉が小さな三角でしか押せない**
  - 原因：開閉ボタン（summary）を右端の44px四方に置いていた。
  - 対応：見出し行のどこを押しても開閉するようにした。
- **版数を上げても、一部のページが古いCSS・JSを読み込む**
  - 原因：ビルド時の置き換えが、特定の古い番号だけを対象にしていた。
  - 対応：任意の番号を置き換える正規表現に変更。

### 2026-11-27 訂正
- 当初「1K参考家賃は5画面以上下」「メタ説明がどの駅もほぼ同じ文面」と記録したが、どちらも誤り。前者は写真下の家賃表示の見落とし、後者はコミット済みの古いHTMLを見たことによる。本番では、家賃は約1.4画面目に表示され、説明文は駅ごとに異なる。

### 2026-11-27（ブランチ `readability/station-text-flow`）
- **単語の途中や、1〜2文字だけの行で改行される**
  - 原因：日本語の折り返しが、文字単位の標準設定のままだった。
  - 対応：文節単位で改行する指定（`word-break: auto-phrase`、`line-break: strict`、`text-wrap: pretty`）を追加。
- **スマホ幅でも「暮らしのポイント」が2列（1行9文字前後）になる**
  - 原因：スマホ用の1列指定が、後ろに書かれた2列指定に上書きされていた（同じ詳細度では、後に書いたものが勝つ）。
  - 対応：後ろ側でスマホ幅の1列指定を上書き。字下げの余白も統一。
- **「条件に合う理由・出典」で情報が分離して見えない**
  - 原因：見出しと本文が同じ左端で、「A／B／C」の羅列が1行に押し込められていた。
  - 対応：本文に左の縦線で字下げし、3項目以上の羅列は箇条書きに変更。

## 再発防止

1. **ページの状態を調べるときは、本番URL（またはプレビューURL）か、`npm run build` 後の出力を見る。** コミットされた `public/` のHTMLだけを見て判断しない。
2. **スマホ用のCSSを書いたら、実際にスマホ幅（390px）で表示して確認する。** 同じ詳細度の指定は後に書いたものが勝つので、ファイルの後ろの方に同じ要素の指定がないか検索する。
3. **「A／B／C」のような羅列は、文字列でつなげずに、項目の一覧として扱う。** 表示側で崩れたら、データの持ち方から見直す。
4. **新しい種類のページや文章を足すときは、スマホの最初の画面で、利用者の知りたい事実（家賃・路線・該当条件）が見えるかを確認する。**
5. **文章を足すときは、出典名・日付・英語の名称を本文に混ぜず、出典欄に分ける。**
6. **CSSやJavaScriptを変えたら、キャッシュ用の版数を更新し、`npm run check` を通す。** 検証が版数を固定で見ているので、更新を忘れると検査が失敗する。
7. **見出し・ラベル・キャプションの文末に「。」を付けない。** 「。」は文章の本文だけに使う。
8. **見出しと本文は、色や太さだけでなく、位置（字下げ・線）でも分ける。** ページ内で同じ見せ方に揃える。
9. **押せる部分は、見た目の範囲と当たり判定を揃える。** 小さなアイコンだけを押せる形にしない。
10. **直した課題は、このファイルの「解決済み」に、日付・原因・対応を書く。** 原因を書いておけば、同じ型の問題を探しやすくなる。
